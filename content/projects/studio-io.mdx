## Project overview

Studio IO is a learning management system built around the complete course journey. Instructors can structure courses into sections and lessons, reorder material, publish rich lesson content, and manage supporting resources. Learners move through enrollment, payment, lesson access, and progress tracking inside the same product.

The application uses Next.js and TypeScript for the product surface, Prisma for persistent course and enrollment data, Stripe for payments, AWS S3 for media, and Tiptap for structured lesson authoring. These systems are connected by explicit application states so an action in the interface has a predictable effect on stored data and learner access.

## Product goals

The central design problem was not simply displaying courses. Studio IO needed to support two distinct workflows without turning the product into separate instructor and learner applications.

For instructors, course structure had to stay flexible while remaining safe to edit. For learners, the interface needed to make the next lesson, progress state, and access status clear. Shared data such as course publication, enrollment, ownership, and payment state had to remain consistent across both experiences.

## Technical approach

### Course authoring as ordered data

Sections and lessons are reorderable through drag-and-drop controls powered by dnd-kit. The visible sequence and the persisted course structure are treated as one workflow, so reorganizing material does not depend on a temporary client-only order. Tiptap provides structured rich-text lesson content while keeping the authoring experience inside the course-management interface.

### Media uploads outside the application server

Course assets can be much larger than ordinary form data. AWS S3 and presigned upload flows allow the browser to send approved files directly to storage instead of routing every byte through the Next.js application server. The application remains responsible for authorization and object metadata while S3 handles the transfer itself.

### Access, enrollment, and payment boundaries

Authentication, course ownership, enrollment, learner progress, and Stripe payment state each affect what a person can view or change. These checks are kept explicit rather than inferred from the interface. Instructor controls depend on ownership, while protected learner content depends on enrollment and payment state.

## Engineering challenges

### Keeping authoring flexible without losing structure

Drag-and-drop interactions feel temporary, but course order is durable product data. Studio IO coordinates interface feedback with persisted ordering so an instructor can reorganize a course without creating ambiguous section or lesson positions.

### Keeping media work from becoming a bottleneck

Large uploads can tie up application resources and make failures difficult to recover from. Presigned storage operations narrow the server's role and make the upload boundary easier to reason about while keeping private storage credentials away from the browser.

### Making permission state understandable

The same lesson can be editable for an instructor, available to an enrolled learner, or unavailable to a visitor. Modeling those states directly makes the interface more predictable and reduces the chance that presentation logic becomes the only access boundary.
